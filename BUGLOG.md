Needs backend-side tracing to confirm, but the frontend chart component itself is not the source.

## Fixed

### Router edit form clobbered stored password + related edit-form bugs (2026-07-17)
- **Backend password-preserving `update()`:** `RouterSerializer.update()` (`Backend/network_management/serializers/router_management_serializer.py`) now pops `password` from `validated_data` when the field is blank/absent, so a `PUT` from the edit form no longer overwrites the stored router password with an empty value.
- **Edit-form password reset/omission:** `useRouterManagement.js` `updateRouter()` strips `password` from the outgoing payload unless the user actually typed a new one; `RouterManagement.jsx` now dispatches `RESET_ROUTER_FORM` before `UPDATE_ROUTER_FORM` on edit-open, so stale state (including a leftover password value) from a previous form session can't bleed into the next edit.
- **`generateSSID` string guard:** `AddRouterForm.jsx`, `EditRouterForm.jsx`, and `RouterFormFields.jsx` all wrap `routerForm.name` in `String(routerForm.name || '')` before `.replace()`, fixing a crash when `name` is `undefined`/non-string when the SSID is auto-generated.
- **`error.status`/`error.details` handler fix:** `useRouterManagement.js` add/update error handling read `error.response?.status` / `error.response.data`, but the shared `api.js` interceptor throws normalized `AuthError` objects with `.status`/`.details` properties (not raw axios `.response`), so those checks never matched and field-level validation errors were silently dropped. Now reads `error.status` / `error.details`.
- **Status:** Fixed, verified against source, deployed to production (`surfzone_web` rebuilt from `nginx/Dockerfile`; `surfzone_backend` restarted to pick up the bind-mounted serializer change).

### RouterOS 7.x login — invalid user name or password (6) despite correct credentials (2026-07-17)
- **Symptom:** Router 5 (RouterOS 7.16) showed "No Routers Found" in the Dashboard / app calls against it failed with `invalid user name or password (6)`, even though the credentials were correct.
- **Root cause:** RouterOS 7.16 only accepts the modern "plaintext" API login; the deprecated challenge-response login is rejected outright, independent of whether the password is right. A direct test with `plaintext_login=True` returned `LOGIN OK`; the app's own `RouterOsApiPool(...)` constructions were failing because most of them omitted `plaintext_login=True`, so they fell back to the deprecated login RouterOS 7.x rejects.
- **Fix:** Added `plaintext_login=True` to all 24 `RouterOsApiPool` constructions (across 8 files) that were missing it: `router_bulk_operations_views.py` (6), `router_session_views.py` (4), `bandwidth_allocation_view.py` (3), `router_user_management_views.py` (2), `network_diagnostics_views.py` (2), `router_monitoring_views.py` (2), `mac_detection.py` (1), `ip_address_model.py` (4). 5 other constructions (`router_bulk_operations_views.py`'s `perform_router_health_check`, both in `router_connection_tester.py`, `router_monitoring_views.py`'s `RouterHealthCheckView`, and `mikrotik_connector.py`'s pooled connector) already had the flag from an earlier partial fix.
- **Status:** Fixed, verified no live `RouterOsApiPool(` construction remains without `plaintext_login`, deployed to production (`surfzone_backend` restarted; bind-mounted, no rebuild needed).

### Router stats 500 — `RouterStats() got unexpected keyword arguments: 'clients'` (2026-07-17)
- **Symptom:** `GET routers/{id}/stats/` 500'd with `RouterStats() got unexpected keyword arguments: 'clients'`; separately, dashboard health/metrics code hit `'Router' object has no attribute 'current_clients'`.
- **Root cause:** `RouterStatsView.get()` (`router_monitoring_views.py`, both the mikrotik and ubiquiti branches) built a `latest_stats` dict keyed `"clients"` and passed it straight into `RouterStats.objects.create(router=router, **latest_stats)` — but the model's real field is `connected_clients_count` (established convention: `RouterListSerializer.get_latest_stats()` already maps `connected_clients_count` → API-facing key `"clients"`, and the frontend's `RouterCard.jsx` reads `stats.clients`). Separately, `Backend/dashboard/views.py` and `Backend/dashboard/serializers.py` referenced a `current_clients` field/annotation that has never existed on `Router`.
- **Fix:** `router_monitoring_views.py` now translates at the DB-write and `history` `getattr()` boundaries only (`connected_clients_count=latest_stats["clients"]`), keeping the `"clients"` key in the outward-facing API response so the frontend contract is unchanged. `dashboard/views.py`'s `health_check.router.current_clients` → `router.get_active_users_count()` (existing method). `dashboard/serializers.py`'s `routers.aggregate(current_load=Sum('current_clients'))` → summed `HotspotUser`/`PPPoEUser` active counts across the queryset (mirrors `get_active_users_count()`'s logic).
- **Status:** Fixed, deployed to production (`surfzone_backend` restarted; bind-mounted, no rebuild needed).

### WebSocket 404 → 403 → real-time tabs stuck (2026-07-17)
- **Symptom:** `wss://.../ws/routers/` 404'd in production; after fixing the serving mode it returned 403; after fixing auth, the router list showed "Real-time Connected" but the Real-Time Monitor and Performance Trends tabs still showed "Connecting…" / 0 values.
- **Root cause (layered):**
  1. **404** — production ran `gunicorn ... surfzone_logic.wsgi:application` (plain WSGI); the full Channels/ASGI stack (`asgi.py`, routing, consumers, `channels`+`channels_redis`) was already correctly built but never served, since WSGI has no upgrade path for WebSockets.
  2. **403** — after switching to an ASGI worker, `RouterConsumer.connect()` correctly rejects `AnonymousUser` (`consumers.py:36-38`, `close(code=4401)` pre-`accept()`), but the frontend (`RouterManagement.jsx:4363`) opened the socket with no credential at all, and `asgi.py`'s only auth layer was plain `channels.auth.AuthMiddlewareStack` (Django session-cookie based) — this app authenticates via JWT in `localStorage`, not session cookies, and browsers can't set an `Authorization` header on a WS handshake.
  3. **Tabs still stuck after the fix** — `RealTimeDashboard.jsx` and `PerformanceMetrics.jsx` both ignore the (now-working) `realTimeData`/`webSocketConnected`/`routerStats`/`systemMetrics` props passed down from `RouterManagement.jsx` and instead call `useNetworkData()` internally, which opens its **own second, separate** WebSocket to the same `/ws/routers/` endpoint via `getWebSocketUrl()` (`useNetworkData.js:427-434`) — with no token appended. That second socket always gets rejected by the same `AnonymousUser` check.
- **Fix (this pass):** `Backend/surfzone_logic/ws_auth.py` (new) — `JWTAuthMiddleware(channels.middleware.BaseMiddleware)`, extracted from the per-consumer query-string JWT logic already used in `sms_automation/consumers.py`; parses `?token=`, validates via SimpleJWT `AccessToken`, resolves the user, and leaves `scope["user"]` unset (not "always AnonymousUser") when no token is present so session auth can still fall back. Wired into `asgi.py` as `JWTAuthMiddleware(AuthMiddlewareStack(URLRouter(websocket_urlpatterns)))`. `RouterManagement.jsx:4363` now appends `?token=${localStorage.getItem(ACCESS_TOKEN)}`, matching the existing `WebSocketService.js:203` convention. `Backend/Dockerfile`'s `CMD` switched from `gunicorn ... wsgi:application` to `gunicorn surfzone_logic.asgi:application -k uvicorn.workers.UvicornWorker`; added `uvicorn[standard]` to `requirements.txt`. `CHANNEL_LAYERS` was already correctly `channels_redis.core.RedisChannelLayer` pointed at the existing `redis` service — no change needed there.
- **Not yet fixed:** `RealTimeDashboard.jsx`/`PerformanceMetrics.jsx`'s own `useNetworkData()` socket (still tokenless) — these two tabs will keep showing "Connecting…" until they're switched to use the parent's props (or `useNetworkData.js`'s `getWebSocketUrl()` gets the same `?token=` treatment). Also confirmed no backend producer ever pushes periodic stats to the `routers_global` group outside of reactive, user-action-triggered `WebSocketManager` calls — the `monitor-router-health` Celery beat entry in `settings.py` references `network_management/tasks.py`, which doesn't exist, and no `celery` service runs in `docker-compose.prod.yml` at all.
- **Status:** Backend serving-mode + auth fix deployed to production (`surfzone_backend` restarted; `surfzone_web` rebuilt). Real-Time Monitor / Performance Trends tabs still broken pending the `useNetworkData()` fix noted above.

### `useHealthMonitoring.js` — `smartFetch` called with wrong signature, causing `e.replace is not a function` (2026-07-17)
- **Symptom:** Recurring `TypeError: e.replace is not a function`, funneled through `api.js`'s error handler as `CLIENT_ERROR`, alongside `"SmartFetch failed after 1 attempts"` in the console.
- **Root cause:** Resolved the deployed bundle's minified `_pe` frame through its source map to `node_modules/axios/lib/helpers/combineURLs.js:13` (`relativeURL.replace(...)`) — confirming the crash was inside axios itself, not any app-level `.replace(`. Traced back to 6 call sites in `useHealthMonitoring.js` (`fetchHealthStats`, `performBulkHealthCheck`, `fetchSystemMetrics`, `fetchConnectionHistory`, `runRouterDiagnostics`, `quickHealthCheck`) that all called `api.smartFetch({method, url, ...}, {options})` — an axios-style config object as the first argument — when `smartFetch`'s real signature is `(url, options)` with `url` a string. The object reached axios's internal `combineURLs` as a non-string `relativeURL` and blew up there.
- **Fix:** All 6 call sites corrected to `smartFetch(url, options)`. The 2 POST sites (`performBulkHealthCheck`, `runRouterDiagnostics`) also had a second, quieter bug: `smartFetch` destructures `options.body` (not `options.data`) as the payload, so `data: payload` would have silently dropped the payload and sent a GET instead of a POST even after fixing the argument order — renamed to `body: payload`. `timeout`/`retries`/`fallbackData`/`showToast` preserved at every site. Grepped the rest of `src/` — no other `smartFetch(` call sites exist.
- **Status:** Fixed, deployed to production (`surfzone_web` rebuilt).

### Docker build context ~1GB, slow web image builds (2026-07-17)
- **Symptom:** `docker build -f nginx/Dockerfile ...` context-transfer step alone took 9+ minutes; no `.dockerignore` existed at the repo root, so the full repo (`.git` 320MB + `Frontend/Dashboard/node_modules` 624MB) was sent as build context every time.
- **Fix:** Added `.dockerignore` (`.git`, `**/node_modules`, `**/*.log`, `**/__pycache__`, `**/.env`, `**/.env.*`). Verified empirically — Docker's bare (non-`**/`-prefixed) ignore patterns only match at the build-context root, not recursively like `.gitignore`, so every pattern needing subdirectory matches uses an explicit `**/` prefix. Confirmed via a throwaway build that context size dropped from ~1GB to 60.9MB, all target paths excluded, and all Vite-build-required paths (`Frontend/Dashboard/src`, `nginx/nginx.conf`, `nginx/Dockerfile`) still present.
- **Status:** Fixed and verified; the subsequent real deploy build's context-transfer step dropped from 9+ minutes to 0.7s.

### Real-Time Monitor / Performance Trends tabs stuck at "Connecting…" — REST props ignored + tokenless second socket (2026-07-17)
- **Symptom:** Follow-on from the WebSocket 404 → 403 entry above — even after the JWT-over-WS fix, `RealTimeDashboard.jsx` and `PerformanceMetrics.jsx` kept showing "Connecting…" / stale 0 values.
- **Root cause:** Both components ignored the working `realTimeData`/`webSocketConnected` props already passed down from `RouterManagement.jsx` and instead opened their own second `/ws/routers/` connection via `useNetworkData()`'s internal `getWebSocketUrl()`, which had no `?token=` appended and was always rejected by the backend's `AnonymousUser` check. Separately, `RouterStatsView` (`router_monitoring_views.py`) never wrote `connection_status`/`last_seen` back onto the `Router` row on a poll, so router "online" state shown elsewhere in the UI stayed stale regardless of the WebSocket fix.
- **Fix:** `useNetworkData.js`'s `getWebSocketUrl()` now appends `?token=${localStorage.getItem(ACCESS_TOKEN)}`, matching the existing convention. `RealTimeDashboard.jsx` now accepts `realTimeData`/`webSocketConnected` as props and ORs its own hook's `webSocketConnected` with the parent's, so either live connection counts. Both components fixed a stale `refreshData` destructure (the hook exports `refresh`, not `refreshData`) that was silently making manual refresh a no-op. `RouterStatsView.get()` (mikrotik + ubiquiti branches) now writes `connection_status='connected'`/`last_seen=now()` on a successful poll and `connection_status='disconnected'` on failure, and distinguishes router-communication errors (`RouterOsApiConnectionError`/`RouterOsApiCommunicationError`, mapped to 502) from other 500s.
- **Status:** Fixed, deployed to production (`surfzone_web` rebuilt; `surfzone_backend` restarted — bind-mounted).

### Dashboard-wide "Network connection failed" toast flood — infinite fetch loop in PerformanceMetrics (2026-07-18)
- **Symptom:** A "Network connection failed - please check your internet" toast (`api.js`'s global axios interceptor, fires on any request that gets no HTTP response at all) appeared repeatedly and seemingly unprovoked, not obviously tied to any one page or action.
- **Root cause:** `PerformanceMetrics.jsx` called `useNetworkData([], activeRouter?.id)` with a fresh `[]` literal on every render. `useNetworkData`'s `fetchInitialData` is a `useCallback` keyed on `[initialRouters, activeRouterId, isAuthenticated]`; since `initialRouters` got a new array reference every render, `fetchInitialData`'s identity changed every render, re-triggering the `useEffect(() => fetchInitialData(), [fetchInitialData])` that calls it — an uncapped render → fetch → state-update → render loop. Each iteration also called `GET /api/network_management/routers/{id}/status/`, a URL never registered in `urls.py` (only `stats/`, `system-metrics/`, `health-check/` exist) — confirmed live via backend logs showing hundreds of 404s to that exact path within minutes. Neither `RealTimeDashboard.jsx` nor `PerformanceMetrics.jsx` actually consumed the hook's own `routerStats` return value (both use the REST-sourced `routerStats` passed down as a prop instead), so the dead endpoint's result was never even read.
- **Fix:** `PerformanceMetrics.jsx` now passes a module-level `EMPTY_ROUTERS` constant instead of an inline `[]`, giving `initialRouters` a stable identity across renders and breaking the loop. The dead `/status/` fetch block in `useNetworkData.js`'s `fetchInitialData` was removed entirely (unused endpoint, unused result).
- **Status:** Fixed, deployed to production (`surfzone_web` rebuilt).

## Future / Architecture

### Multi-tenant SaaS (white-label per-ISP) — deferred, months out
- **Audit (2026-07-03):** Found NO existing multi-tenancy. `UserAccount` has a flat `user_type` string (client/staff/admin) but no tenant FK; no ISP/Organization/Tenant container model exists anywhere; no RBAC beyond DRF `IsAuthenticated`/`is_staff`; every list endpoint (clients, plans, routers) returns ALL rows to any authenticated user — zero tenant scoping; frontend permissions plumbing is vestigial (wired but backend never populates it, so always `[]`; role-gating actually keys off `user_type`).
- **Conclusion:** Clean-slate build, not a retrofit.
- **Plan (per owner):** Finish + stabilize the single-tenant platform first, THEN clone and adapt into multi-tenant.
- **Build order when tackled:**
  1. Tenant/ISP model
  2. Tenant FK on all owned models + migration
  3. Central auto-scoping (base manager/mixin, enforced by default — critical for data isolation)
  4. RBAC role hierarchy: super → ISP-admin → sub-admin/marketer
  5. Per-ISP branding + PPPoE/captive-portal pages read from tenant
- **WATCH:** Router list cache key is global (`routers:list:...`) with no tenant namespace — would leak across tenants; revisit all cache keys during tenancy work.
- **Also:** Hardcoded "Diconden" branding (6 files + 3 `dicondenlogo.png` assets) is intentionally NOT swapped to "SurfZone" — it should become dynamic per-tenant, so leave until tenancy is built (or do a temporary swap only if a real single-tenant launch needs it).
