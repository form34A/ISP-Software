### WebSocket 404 → 403 → real-time tabs stuck (2026-07-17)
- **Symptom:** `wss://.../ws/routers/` 404'd in production; after fixing the serving mode it returned 403; after fixing auth, the router list showed "Real-time Connected" but the Real-Time Monitor and Performance Trends tabs still showed "Connecting…" / 0 values.
- **Root cause (layered):**
  1. **404** — production ran `gunicorn ... surfzone_logic.wsgi:application` (plain WSGI); the full Channels/ASGI stack (`asgi.py`, routing, consumers, `channels`+`channels_redis`) was already correctly built but never served, since WSGI has no upgrade path for WebSockets.
  2. **403** — after switching to an ASGI worker, `RouterConsumer.connect()` correctly rejects `AnonymousUser` (`consumers.py:36-38`, `close(code=4401)` pre-`accept()`), but the frontend (`RouterManagement.jsx:4363`) opened the socket with no credential at all, and `asgi.py`'s only auth layer was plain `channels.auth.AuthMiddlewareStack` (Django session-cookie based) — this app authenticates via JWT in `localStorage`, not session cookies, and browsers can't set an `Authorization` header on a WS handshake.
  3. **Tabs still stuck after the fix** — `RealTimeDashboard.jsx` and `PerformanceMetrics.jsx` both ignore the (now-working) `realTimeData`/`webSocketConnected`/`routerStats`/`systemMetrics` props passed down from `RouterManagement.jsx` and instead call `useNetworkData()` internally, which opens its **own second, separate** WebSocket to the same `/ws/routers/` endpoint via `getWebSocketUrl()` (`useNetworkData.js:427-434`) — with no token appended. That second socket always gets rejected by the same `AnonymousUser` check.
- **Fix (this pass):** `Backend/surfzone_logic/ws_auth.py` (new) — `JWTAuthMiddleware(channels.middleware.BaseMiddleware)`, extracted from the per-consumer query-string JWT logic already used in `sms_automation/consumers.py`; parses `?token=`, validates via SimpleJWT `AccessToken`, resolves the user, and leaves `scope["user"]` unset (not "always AnonymousUser") when no token is present so session auth can still fall back. Wired into `asgi.py` as `JWTAuthMiddleware(AuthMiddlewareStack(URLRouter(websocket_urlpatterns)))`. `RouterManagement.jsx:4363` now appends `?token=${localStorage.getItem(ACCESS_TOKEN)}`, matching the existing `WebSocketService.js:203` convention. `Backend/Dockerfile`'s `CMD` switched from `gunicorn ... wsgi:application` to `gunicorn surfzone_logic.asgi:application -k uvicorn.workers.UvicornWorker`; added `uvicorn[standard]` to `requirements.txt`. `CHANNEL_LAYERS` was already correctly `channels_redis.core.RedisChannelLayer` pointed at the existing `redis` service — no change needed there.
- **Not yet fixed:** `RealTimeDashboard.jsx`/`PerformanceMetrics.jsx`'s own `useNetworkData()` socket (still tokenless) — these two tabs will keep showing "Connecting…" until they're switched to use the parent's props (or `useNetworkData.js`'s `getWebSocketUrl()` gets the same `?token=` treatment). Also confirmed no backend producer ever pushes periodic stats to the `routers_global` group outside of reactive, user-action-triggered `WebSocketManager` calls — the `monitor-router-health` Celery beat entry in `settings.py` references `network_management/tasks.py`, which doesn't exist, and no `celery` service runs in `docker-compose.prod.yml` at all.
- **Status:** Backend serving-mode + auth fix deployed to production (`surfzone_backend` restarted; `surfzone_web` rebuilt). Real-Time Monitor / Performance Trends tabs still broken pending the `useNetworkData()` fix noted above.

### `useHealthMonitoring.js` — `smartFetch` called with wrong signature, causing `e.replace is not a function` (2026-07-17)
- **Symptom:** Recurring `TypeError: e.replace is not a function`, funneled through `api.js`'s error handler as `CLIENT_ERROR`, alongside `"SmartFetch failed after 1 attempts"` in the console.
- **Root cause:** Resolved the deployed bundle's minified `_pe` frame through its source map to `node_modules/axios/lib/helpers/combineURLs.js:13` (`relativeURL.replace(...)`) — confirming the crash was inside axios itself, not any app-level `.replace(`. Traced back to 6 call sites in `useHealthMonitoring.js` (`fetchHealthStats`, `performBulkHealthCheck`, `fetchSystemMetrics`, `fetchConnectionHistory`, `runRouterDiagnostics`, `quickHealthCheck`) that all called `api.smartFetch({method, url, ...}, {options})` — an axios-style config object as the first argument — when `smartFetch`'s real signature is `(url, options)` with `url` a string. The object reached axios's internal `combineURLs` as a non-string `relativeURL` and blew up there.
- **Fix:** All 6 call sites corrected to `smartFetch(url, options)`. The 2 POST sites (`performBulkHealthCheck`, `runRouterDiagnostics`) also had a second, quieter bug: `smartFetch` destructures `options.body` (not `options.data`) as the payload, so `data: payload` would have silently dropped the payload and sent a GET instead of a POST even after fixing the argument order — renamed to `body: payload`. `timeout`/`retries`/`fallbackData`/`showToast` preserved at every site. Grepped the rest of `src/` — no other `smartFetch(` call sites exist.
- **Status:** Fixed, deployed to production (`surfzone_web` rebuilt).

### Dashboard-wide "Network connection failed" toast flood — infinite fetch loop in PerformanceMetrics (2026-07-18)
- **Symptom:** A "Network connection failed - please check your internet" toast (`api.js`'s global axios interceptor, fires on any request that gets no HTTP response at all) appeared repeatedly and seemingly unprovoked, not obviously tied to any one page or action.
- **Root cause:** `PerformanceMetrics.jsx` called `useNetworkData([], activeRouter?.id)` with a fresh `[]` literal on every render. `useNetworkData`'s `fetchInitialData` is a `useCallback` keyed on `[initialRouters, activeRouterId, isAuthenticated]`; since `initialRouters` got a new array reference every render, `fetchInitialData`'s identity changed every render, re-triggering the `useEffect(() => fetchInitialData(), [fetchInitialData])` that calls it — an uncapped render → fetch → state-update → render loop. Each iteration also called `GET /api/network_management/routers/{id}/status/`, a URL never registered in `urls.py` (only `stats/`, `system-metrics/`, `health-check/` exist) — confirmed live via backend logs showing hundreds of 404s to that exact path within minutes. Neither `RealTimeDashboard.jsx` nor `PerformanceMetrics.jsx` actually consumed the hook's own `routerStats` return value (both use the REST-sourced `routerStats` passed down as a prop instead), so the dead endpoint's result was never even read.
- **Fix:** `PerformanceMetrics.jsx` now passes a module-level `EMPTY_ROUTERS` constant instead of an inline `[]`, giving `initialRouters` a stable identity across renders and breaking the loop. The dead `/status/` fetch block in `useNetworkData.js`'s `fetchInitialData` was removed entirely (unused endpoint, unused result).
- **Status:** Fixed, deployed to production (`surfzone_web` rebuilt).

### WAN sampler `interval_seconds` inflated by ping duration (2026-07-21)
- **Symptom:** During Stage 1 manual testing of the new WAN congestion sampler (`sample_wan` management command, `Backend/network_management/management/commands/sample_wan.py`), `interval_seconds` between two consecutive `WanSample` rows for the same interface was consistently ~9-10s shorter than the true wall-clock gap between runs, inflating `down_mbps`/`up_mbps` by roughly one ping's worth of time each cycle (~11% in the first observed test).
- **Root cause:** `handle()` computed `interval_seconds` (`now() - prev.timestamp`) and read the interface counters *before* issuing the `/ping` probe, but `WanSample.timestamp` is `auto_now_add` and only gets stamped when the row is saved — which happened *after* the ~10s ping (`--ping-count 10`, ~1/s). So every row's saved timestamp already included its own ping delay, understating the next row's computed interval by one ping's duration.
- **Fix:** Reordered `handle()` so `/ping` runs first, then the interface counters are read and the row saved immediately after, back-to-back — so `timestamp` sits right next to the counter read with no ping delay in between.
- **Status:** Fixed, verified via two manual `sample_wan` runs ~95s apart: stored `interval_seconds` (95.368708s) matched the true wall-clock gap between row timestamps (95.369606s) to within ~0.001s. Not yet scheduled via cron (Stage 1 scope only).

### Diagnostics history chart — crash on missing/404 speed-test history (2026-07-21)
- **Symptom:** The speed-test history chart on `NetworkDiagnostics.jsx` could throw and blank the page whenever `historicalData.isp`/`.client` wasn't a well-formed `{minute,hour,day,month}` object — e.g. if a fetch failure ever left stale or oddly-shaped data in state, or if `chartData` ran before the first successful fetch populated real data.

[]` before use, so it can no longer throw regardless of shape. `fetchHistoricalData`'s catch now specifically checks `error.response?.status === 404` and suppresses the toast in that case (still resets state to `EMPTY_HISTORY`) while keeping the toast for real errors (500s, network failures).

## Future / Architecture

- **Audit (2026-07-03):** Found NO existing multi-tenancy. `UserAccount` has a flat `user_type` string (client/staff/admin) but no tenant FK; no ISP/Organization/Tenant container model exists anywhere; no RBAC beyond DRF `IsAuthenticated`/`is_staff`; every list endpoint (clients, plans, routers) returns ALL rows to any authenticated user — zero tenant scoping; frontend permissions plumbing is vestigial (wired but backend never populates it, so always `[]`; role-gating actually keys off `user_type`).

  3. Central auto-scoping (base manager/mixin, enforced by default — critical for data isolation)
  4. RBAC role hierarchy: super → ISP-admin → sub-admin/marketer
