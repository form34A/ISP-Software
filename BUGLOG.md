### GET /api/account/profile/ 500 - profile_pic accessed on a UserAccount field that doesn't exist (2026-07-23)
- **Symptom:** `GET /api/account/profile/` (backing the Dashboard's Admin Profile page) returned a 500 on every call: `{"detail":"Failed to load profile data","error":"'UserAccount' object has no attribute 'profile_pic'"}`.
- **Root cause:** `AdminProfileView.get()`/`.put()` (`account/api/views/admin_view.py`) accessed `user.profile_pic.url` directly, but `profile_pic` was never added as a real `UserAccount` model field - only referenced in this view and in `AdminProfileSerializer`, never declared on the model. Confirmed via `hasattr(user, 'profile_pic')` → `False` and a live curl reproducing the 500.
- **Fix:** Both call sites now do `getattr(user, 'profile_pic', None)` first and only build the URL when that's truthy, returning `None` (JSON `null`) otherwise - the same defensive pattern `metadata` already used before it got a real column. No `profile_pic` model field or migration added in this pass; that's a separate feature decision (see media-serving/Pillow findings below).
- **Also found, not fixed:** `PUT /api/account/profile/` still 500s for an unrelated reason - see the matching entry under Open (`AdminProfileSerializer.Meta.fields` lists `is_2fa_enabled`, which isn't a real model field or an explicitly-declared serializer field, so `is_valid()` raises `ImproperlyConfigured` before ever reaching the profile_pic lines this fix touched).
- **Media serving, for whoever picks up the real profile-picture feature:** `MEDIA_ROOT`/`MEDIA_URL` are configured (`Backend/media/`, `/media/`, with a pre-existing empty `profile_pics/` subdirectory) and the Backend volume is a host bind-mount (`./Backend:/app`) so uploads would persist. But end-to-end media serving doesn't currently work in this deployment: nginx's `/media/` location proxies to Django rather than serving from a shared volume, and Django's own `static(MEDIA_URL, ...)` call in `urls.py` is a no-op when `DEBUG=False` (confirmed `DJANGO_DEBUG=false` in this environment) - so today a request to `/media/...` would 404 all the way through. `Pillow`, required for Django's `ImageField`, is also not installed (only commented out in `requirements.txt`). A real field needs: the model field + migration, Pillow installed, and either an explicit non-DEBUG-gated Django media URL pattern or (cleaner) a shared volume + nginx `alias` for `/media/`.
- **Status:** Fixed (GET only), deployed to production (`surfzone_backend` restarted).

### Router stats: scheduled collector + fix memory-as-MB and fake-0 temperature in the write path (2026-07-23)
- **Symptom:** The only writer of `RouterStats` was the browser-driven `RouterStatsView.get()` (`GET /api/network_management/routers/<pk>/stats/`), so rows only landed while someone had the Router Management page open, and `RouterConnectionTest` had gone 5+ days stale — both starved the dashboard's 1-hour rolling averages. Separately, the write path itself stored `memory` as raw free-memory megabytes (not the 0-100 percentage the field/dashboard expect — e.g. `188.85` on a 256MB board instead of the real ~26% used) and defaulted `temperature` to `0` whenever a board reported no `cpu-temperature` key, indistinguishable from a genuine 0°C reading.
- **Root cause:** `RouterStatsView.get()` (`network_management/api/views/router_management/router_monitoring_views.py:76-80`, pre-fix) computed `memory_mb = free_mem / 1024 / 1024` and stored that directly into `RouterStats.memory`; `temperature` used `safe_float(system.get("cpu-temperature", 0))`, defaulting to `0` on absence rather than `None` (the field is already `null=True, blank=True` — no migration needed). No scheduler existed for this table at all — confirmed via `crontab -l`, no celery/beat service in `docker-compose.prod.yml`, and `network_management/tasks.py` doesn't exist.
- **Fix:** New shared helper `network_management/utils/router_stats_helpers.py` (`parse_system_resource()`) computes `memory_percent = (total-memory - free-memory) / total-memory * 100` and returns `temperature=None` when the router's `/system/resource` response has no `cpu-temperature` key at all (confirmed live against router 6, a wired hEX S board with no thermal sensor — the key is simply absent). New management command `network_management/management/commands/sample_router_stats.py` samples every `is_active=True` router (or one via `--router-id`) on a schedule: writes a `RouterStats` row via the shared helper, times the round-trip into a `RouterConnectionTest` row (`success`/`response_time`), and updates `Router.firmware_version`/`connection_status`. Per-router failures are caught and logged as a `success=False` `RouterConnectionTest` row without stopping the rest of the fleet. `RouterStatsView.get()` now calls the same shared helper (both mikrotik and ubiquiti branches) instead of its own local `memory_mb`/hardcoded-`0`-temperature logic, so the browser-driven and scheduled write paths can't drift apart again. `upload_speed`/`download_speed` intentionally left untouched (default `0`) — grepped every consumer and confirmed nothing renders a real value from those two columns (the only live UI reads come from a different, already-separate transient dict that never included them); throughput is intentionally left to the existing `sample_wan` collector rather than double-polling `/interface`.
- **Status:** Fixed, deployed to production (`surfzone_backend` restarted, no migration required). Note: the ~111 pre-existing `RouterStats` rows still hold megabyte values in `memory` and will keep skewing the dashboard's 1-hour average until they age out naturally.

### Dashboard-wide "Network connection failed" toast flood — infinite fetch loop in PerformanceMetrics (2026-07-18)
- **Symptom:** A "Network connection failed - please check your internet" toast (`api.js`'s global axios interceptor, fires on any request that gets no HTTP response at all) appeared repeatedly and seemingly unprovoked, not obviously tied to any one page or action.
- **Root cause:** `PerformanceMetrics.jsx` called `useNetworkData([], activeRouter?.id)` with a fresh `[]` literal on every render. `useNetworkData`'s `fetchInitialData` is a `useCallback` keyed on `[initialRouters, activeRouterId, isAuthenticated]`; since `initialRouters` got a new array reference every render, `fetchInitialData`'s identity changed every render, re-triggering the `useEffect(() => fetchInitialData(), [fetchInitialData])` that calls it — an uncapped render → fetch → state-update → render loop. Each iteration also called `GET /api/network_management/routers/{id}/status/`, a URL never registered in `urls.py` (only `stats/`, `system-metrics/`, `health-check/` exist) — confirmed live via backend logs showing hundreds of 404s to that exact path within minutes. Neither `RealTimeDashboard.jsx` nor `PerformanceMetrics.jsx` actually consumed the hook's own `routerStats` return value (both use the REST-sourced `routerStats` passed down as a prop instead), so the dead endpoint's result was never even read.
- **Fix:** `PerformanceMetrics.jsx` now passes a module-level `EMPTY_ROUTERS` constant instead of an inline `[]`, giving `initialRouters` a stable identity across renders and breaking the loop. The dead `/status/` fetch block in `useNetworkData.js`'s `fetchInitialData` was removed entirely (unused endpoint, unused result).
- **Status:** Fixed, deployed to production (`surfzone_web` rebuilt).

### WAN sampler `interval_seconds` inflated by ping duration (2026-07-21)
- **Symptom:** During Stage 1 manual testing of the new WAN congestion sampler (`sample_wan` management command, `Backend/network_management/management/commands/sample_wan.py`), `interval_seconds` between two consecutive `WanSample` rows for the same interface was consistently ~9-10s shorter than the true wall-clock gap between runs, inflating `down_mbps`/`up_mbps` by roughly one ping's worth of time each cycle (~11% in the first observed test).
- **Root cause:** `handle()` computed `interval_seconds` (`now() - prev.timestamp`) and read the interface counters *before* issuing the `/ping` probe, but `WanSample.timestamp` is `auto_now_add` and only gets stamped when the row is saved — which happened *after* the ~10s ping (`--ping-count 10`, ~1/s). So every row's saved timestamp already included its own ping delay, understating the next row's computed interval by one ping's duration.
- **Fix:** Reordered `handle()` so `/ping` runs first, then the interface counters are read and the row saved immediately after, back-to-back — so `timestamp` sits right next to the counter read with no ping delay in between.
- **Status:** Fixed, verified via two manual `sample_wan` runs ~95s apart: stored `interval_seconds` (95.368708s) matched the true wall-clock gap between row timestamps (95.369606s) to within ~0.001s. Not yet scheduled via cron (Stage 1 scope only).
